# T-165.1 privileged aligner and internal orchestrator topology

**Owning Task:** T-165.1
**Overall confidence:** MEDIUM-HIGH until the nested writable-worker integration Check passes
**Supersedes:** doc-113's delegated-aligner recommendation

## Settled operator contract

The visible project-home Pi is the privileged aligner and sole operational conversational interface. Orchestration and work Actors are fully internal. The aligner has broad epistemic/presentational access, typed coordination, and no execution or operator-disposition authority. It resolves supplied citations rather than investigating. The architect remains a direct, operator-invoked independent audit surface after the fact. Calibration state is applied to aligner behavior later and is never exposed to the aligner. No speculative anti-chatter cap is added.

## Recommendation

Use one session-long, nested, fanout-capable `orchestrator` child beneath the visible aligner:

```
operator ↔ aligner root (depth 0)
                    ↕ typed qq broker
             orchestrator child (depth 1)
                    ↕ native pi-subagents fanout
 implementer / reviewer / researcher / observer (depth 2)
```

The aligner process launches the one trusted orchestrator mechanically through pi-subagents' versioned async RPC. The aligner model never receives generic `subagent`, intercom, shell, repository, delivery, Backlog, GitHub, or Herdr tools. A narrow qq-owned broker carries exact typed exchanges, supplied-evidence capabilities, trace references, and lifecycle receipts. The orchestrator receives the ordinary execution/orchestration capabilities and explicit child-safe `subagent` authority needed to dispatch existing trusted roles.

This topology creates no second Herdr work tab or competing operator surface, preserves one warm orchestrator session for the visible aligner session, and keeps worker runs in pi-subagents' nested lifecycle/artifact tree. A sibling/background Pi is rejected because it would reintroduce a visible tab or require qq to own a second unsupported top-level process lifecycle. A stateless controller is rejected because it would recreate the workflow/state machine qq removed and replay orchestration context on every exchange.

## Owner-verified findings

- **[HIGH — observed] Root role confinement is supportable with current pinned Pi without a direct model-runtime fork.** Pi accepts `--no-extensions` plus exact repeated `--extension`, `--no-skills`, `--no-prompt-templates`, `--no-context-files`, and `--no-tools` launch flags (`Pi README`, “Resource Options” and “Tool Options”). An exact root extension can register only aligner tools, activate exactly those tools with `pi.setActiveTools`, replace the system prompt in every `before_agent_start`, and fail closed on any registry/profile mismatch (`Pi docs/extensions.md:521-556,1338-1343,1622-1640`). qq's `bin/pi` is already the sole verified PATH-level wrapper around the pinned patched runtime (`README.md:58-63`; `bin/pi`; `bin/qq-pi-runtime:1434-1479`).

- **[HIGH — observed] Current pi-subagents supports exactly two nested levels by default and admits child fanout only when the child manifest explicitly names `subagent`.** The inherited maximum may be tightened but not loosened by a child (`pi-subagents/README.md:1570-1588`; `src/shared/types.ts:1297,1351-1376`). Nested run ids, sessions, status, artifacts, and events remain attached to the parent run.

- **[HIGH — observed] A trusted orchestrator role can be source-selected like existing workers.** `.pi/extensions/qq-subagent-env.ts:35-64` owns the exact trusted manifest map and `bin/qq-dispatch`; current dispatch fails closed on every unknown role (`bin/qq-dispatch:89-97`). An orchestrator manifest can use replacement prompt, no inherited project context/Skills, strict tools, empty normal extensions, and child-only qq environment/channel extensions. pi-subagents verifies every declared tool before the first model turn (`pi-subagents/README.md:739-815`; `src/runs/shared/pi-args.ts:112-173`).

- **[HIGH — observed] The nested orchestrator's outer Landstrip boundary constrains all worker descendants.** `qq-dispatch` launches Landstrip outside the child Pi and its entire process tree (`bin/qq-dispatch:348-373`). The present renderer grants writes only to the dispatch run directory and, for `workspace-write`, the assigned worktree and its Git directories (`bin/lib/qq-render-landstrip-policy.mjs:122-151`). Therefore a read-only or current-worktree-only outer policy cannot support descendants writing future assigned Change worktrees. The orchestrator policy must be a reviewed superset over qq's Repository/Git/worktree/runtime roots; every nested worker retains its narrower existing policy.

- **[HIGH — observed] pi-subagents' native supervisor channel is not the permanent aligner protocol.** Its public parent tool can only list/pending/reply; the child must initiate each ask and payloads are prose (`src/intercom/native-supervisor-channel.ts:224-282,561-588`). The versioned public RPC supports spawn/status/interrupt/stop, not arbitrary session messages (`src/extension/rpc.ts:173-402`). A qq-owned, schema-validated broker is therefore necessary to let the aligner initiate intent/status/evidence/disposition exchanges without exposing generic intercom or importing unstable vendor internals.

- **[HIGH — recommendation] The broker is transport, not a workflow engine.** It starts/stops/reconnects the sole orchestrator, validates exact request/response schemas, journals raw packets, registers evidence capabilities, waits for one correlated response, and seals the trace. It does not choose workers, order work, interpret completions, manage Tasks, or make delivery judgments; those remain in the internal orchestrator.

- **[HIGH — recommendation] Use capability ids for evidence, never aligner-supplied paths.** The orchestrator/controller registers an exact canonical file or trace range with media type, digest, source exchange, and expiry. `open_supplied_evidence` accepts only that opaque id and a bounded subrange; it exposes no directory, glob, search, neighboring path, arbitrary URI, or path-to-capability conversion. Exact operator-supplied objects may also be registered without granting neighboring access.

- **[HIGH — observed] The existing architect command is not independent.** `/architect` currently injects an architect prompt into the active session with `pi.sendUserMessage` (`extensions/qq-architect.ts:283-368`). T-165.1 must instead provide a distinct immutable architect root profile/session that opens a sealed after-the-fact alignment/work package directly. It may be created only on explicit operator invocation, with no automatic focus or focus-restoration command.

- **[HIGH — recommendation] Preserve the full trace in mode-restricted XDG state.** The journal retains verbatim operator text, labeled aligner interpretations, unmodified orchestrator packets, exact dispositions, capability metadata/digests, nested run ids, and qq trace/span ids. At finalization it is sealed and linked from observer/architect material. Calibration state is not part of the package and is not readable by the aligner.

## Typed authority boundary

The aligner may send only `intent`, `clarification`, `status_request`, `evidence_request`, `analysis_request`, or `disposition`. Every packet carries version, Change/exchange/trace identity, exact operator wording where applicable, and `reply_to`. A disposition must identify an open decision and retain the verbatim operator response. The schema has no agent, role, task, cwd, branch, command, priority, schedule, dispatch, retry, stop, merge, Task-state, or delivery-state field.

The orchestrator returns only a typed projection: lifecycle state, response kind, facts/inferences/recommendation/uncertainties, open decision packets, evidence and trace capabilities, nested work receipts, and next expected operator input. The unmodified internal packet stays in the trace. The broker refuses unknown fields and stale correlation ids.

## Consequential implementation fact

The recommended nested topology requires the orchestrator process to hold a broader outer Landstrip write boundary than current worker roles so writable grandchildren can function. This does **not** give that authority to the aligner; it recognizes the fully internal orchestrator as the execution authority replacing today's accountable root. Worker policies still narrow each descendant. Avoiding this consequence would require a root-side controller to dispatch all workers for the orchestrator, which recreates the workflow engine rejected above.

## Remaining evidence gaps

- The exact orchestrator superset paths must be enumerated and proven with a real nested implementer writing only its assigned linked worktree.
- Session shutdown/handoff must prove the session-long orchestrator terminates or transfers cleanly without an orphan and without focus manipulation.
- The broker protocol and root-profile flags are source-supported but not yet implemented or integration-tested in qq.
- No aligner/orchestrator latency measurement exists; UAT must observe it without adding speculative loop controls.
